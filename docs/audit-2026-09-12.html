The build crashed because it was built without its keys

A full audit of the Expo attendance app, run against the crash reported on the first installable build. The crash has one cause, it is proven below, and it is fixed. Nineteen further findings came out of the sweep — ten are fixed in this pass, nine are recorded for a decision.

The crash

One cause, reproducible on demand, with nothing wrong in the app's own logic. The dev server worked the entire time it was broken, which is why it was not caught earlier.

F01 · Blocker

The app dies before React mounts, so there is no screen to show an error on

  1. Expo reads EXPO_PUBLIC_* variables at build time and inlines their literal values into the JavaScript bundle. They are not read at runtime.
  2. Those two values live in .env, and .env is listed in .gitignore. A build server clones the repository, so it never sees the file.
  3. The bundle is therefore compiled with both values as undefined.
  4. createClient(undefined, undefined) throws supabaseUrl is required. at module scope — while the bundle is still evaluating, before React mounts and before any error boundary exists. The process goes away on the splash screen with nothing on screen and nothing in the app to explain it.

Proof — the emitted bundle, built the way a build server builds it

$ EXPO_NO_DOTENV=1 npx expo export --platform android --no-bytecode
$ grep -o "createClient)(void 0,void 0" index-*.js
createClient)(void 0,void 0

The same command after the fix

$ EXPO_NO_DOTENV=1 npx expo export --platform android --no-bytecode
$ grep -o "unconfigured.invalid" index-*.js
unconfigured.invalid        # placeholder — no throw, ConfigError screen renders

What was changed

  • eas.json — every build profile now carries the two EXPO_PUBLIC_ values in an env block, so a build has them whether or not .env exists.
  • src/lib/supabase.js — never throws. Missing configuration becomes an exported value, supabaseConfigError, and the client falls back to a host in the reserved .invalid TLD so a stray request can never reach somebody else's server.
  • src/components/ConfigError.js — a new screen that says what is missing, in words for the person holding the phone and then for the person who can fix it.
  • docs/BUILD.md — the rule about which secrets may enter a build, written down. The service-role key must never go in: it bypasses every access rule in the database, and anything inlined into a bundle is readable by anyone holding the APK.

Fixed in this pass

Nine further defects, found by reading every module and by driving the running app against the live school database. All are applied and the Android bundle builds clean.

F02

The Dashboard reported “All students accounted for” when it had failed to load anything HighFixed

DashboardScreen destructured students, duties, records and refresh from the data context but never read loading or error. A dropped connection leaves duties empty — and every count on the screen derived from an empty list reads as good news. The calm hero rendered, over “0 of 0 checkpoints marked so far”, on the one screen in this app whose entire job is to say when a child is unaccounted for.

Fixed — “we do not know” is now a third state, distinct from all-clear and from someone-is-missing: a neutral hero, plus the real reason and a retry, so offline never reads as safe.

src/screens/DashboardScreen.js:131 · new loadFailed / stale guards

F03

No error boundary anywhere in the tree HighFixed

A render-time exception below the root unmounts the whole app. In a release build that shows nothing at all — a blank screen, or a process that simply goes away, which every user reports as “it crashed” with no detail to act on.

Fixed — a new ErrorBoundary wraps everything, outside every provider so a throw from any of them still lands somewhere that can draw. Styling is literal rather than themed, because the theme is one of the things that could be broken.

src/components/ErrorBoundary.js (new) · App.js:107

F04

A font that never loaded left the app frozen on the splash screen HighFixed

The splash was held until fontsLoaded turned true, and the error value from useFonts was discarded. A loader that fails or never settles therefore parked the app on the splash indefinitely. To a teacher at Mangalarati that is indistinguishable from a crash.

Fixed — the error is honoured and a six-second ceiling added. The app is perfectly usable in the system font; a missing typeface is not a reason to withhold the register.

App.js:50 · FONT_TIMEOUT_MS

F05

The “Deactivate” button on a staff member did nothing at all HighFixed

The Roster's staff row opened a dialog.confirm with a red, destructive “Deactivate” button and no onConfirm behind it. Tapping it dismissed the dialog and changed nothing. A coordinator who had just “removed” somebody would keep seeing them on the roster and conclude the app was stale rather than that the action had never happened. Deactivation is built nowhere — not in the app, not in the database.

Fixed — now a plain detail dialog that says deactivation is not available yet and who to ask. The whole codebase was then swept for the same shape: no other confirm is missing its handler, and no touchable is missing its onPress.

src/screens/RosterScreen.js:501

F06

A failed sign-in attempt could show nothing whatsoever HighFixed

handleContinue had a try and a finally and no catch. Supabase reports a wrong password through its returned error, but it throws for a transport failure — no signal, DNS down, a captive portal on the school wi-fi. That throw escaped as an unhandled rejection: the button came back to life, no message appeared, and the teacher was left tapping Sign in at a screen that had already given up.

Fixed — caught and routed through describeError, which already knows how to tell offline apart from a permission refusal and from a missing migration.

src/screens/LoginScreen.js:270

F07

“Forgot password?” was a dead link MediumFixed

A styled, tappable link with no handler — on the screen where somebody who cannot get in is most likely to tap it. Self-service reset needs a redirect URL and a deep link, neither of which this build has.

Fixed — it now says who can actually reset a password, rather than pretending to do it.

src/screens/LoginScreen.js · Forgot password control

F08

An overseer could be shown an empty class over a record that was already full MediumFixed

The marking screen seeded its marks from the stored record at mount only. Open a submitted checkpoint while the Duties list's background refresh is still in flight and the marks arrive to a screen that has already decided it is empty — a full class shown as all-present, with a Save button in front of an overseer.

Fixed — the record is adopted once, the first time it appears, and never afterwards, so a later refresh cannot discard marks somebody is in the middle of making.

src/screens/DutyMarkingScreen.js:108

secShort ended in sec[0], which throws on a null or empty section — inside the map over the whole 415-student register, which every screen in the app awaits. One bad import row, and nothing loads.

Fixed — a missing section now renders as a dash on that one student.

src/lib/students.js:17

These need a decision or a piece of work beyond a defect fix. None of them stops the pilot. The first two are the ones worth reading before the school is told the system is watching.

F11 · Nothing sends the alert. The app knows; nobody is told.

The went-missing check itself works, and was watched working against the live database during this audit: forty-five students correctly classed as present earlier, absent now, each naming the checkpoint they were last seen at. But supabase/functions/ does not exist. send-summary and cron-reminders — the summary email on every submission, the immediate alert to Coordinator, MOD and Principal, and the whole missed-checkpoint escalation ladder — are unbuilt.

Until they exist, the safety net only catches a child if somebody happens to open the Dashboard. That is the difference between the system described to the school and the system installed, and it should be stated plainly before the pilot rather than discovered during it.

F12 · Twenty-six development logins share one password, on the live project

supabase/seed-auth-users.sql issues every staff row an account with the password Gurukula@123, and those accounts answer right now on the school's real Supabase project — this audit signed in as the coordinator with them. The file says so in its own header. They have to be deleted and replaced with real logins before any genuine student data is entered.

F13

The Dashboard mounts every alert and every checkpoint at once MediumOpen

It is a plain ScrollView, not a virtualised list. On today's data that is 45 alert cards plus 24 checkpoint rows — roughly 7,000px of content, each card running its own entrance animation, all mounted before the first frame. The marking screen and the register both virtualise properly; this screen is the one that does not, and it is the screen the coordinator opens at 4:30 AM.

src/screens/DashboardScreen.js:307, 327 · open.map / duties.map

F14

Every tab focus refetches the whole day, one query per submitted checkpoint MediumOpen

Four screens call refresh() in useFocusEffect, and SchoolDataContext.load issues one attendance query per submitted duty — 24 today, more as the checkpoint list grows. Switching tabs therefore costs 27 round trips on school wi-fi. fetchDayAttendance in lib/history.js already solves exactly this with a single paged .in(duty_id, …) query; the live path should use the same shape.

src/context/SchoolDataContext.js · load()

F15

The Roster's student tab fetches its own second copy of the register MediumOpen

StudentsTab calls useStudents() rather than reading useSchoolData(), so opening that tab pulls all 415 rows again when they are already in memory. CLAUDE.md §3 says every screen reads from the shared context “rather than fetching its own copy”; this is the one place that does not.

src/screens/RosterScreen.js:725

F16

“33/36 present” with no absent count reads as three unexplained children MediumOpen

The submitted-duty caption prints present-of-total and the absent count, and omits the elsewhere figure — the children at home, in the sick bay or on an outing. Seen live on today's data: “33/36 present · Dharmshila Mt”, three students unaccounted for as far as anyone reading the line can tell, when in fact all three are accounted for. The distinction between absent and elsewhere is the core distinction in this app; the summary line is the one place it is dropped.

src/screens/DutiesScreen.js:475 · DoneRow

F17

A failed sign-up leaves an orphan request in the coordinator's queue MediumOpen

submitAccessRequest runs before supabase.auth.signUp — deliberately, so the request is visible even though email confirmation withholds the session. But when the sign-up then fails (address already registered, rate limited), the request stays behind, from somebody who has no account to approve.

src/screens/RegisterScreen.js:76

F18

Eleven packages are behind the versions SDK 57 expects MediumOpen

Including expo itself (57.0.12 against 57.0.22) and react-native (0.86.2 against 0.86.3). All patch-level within the same SDK, so the upgrade is low risk — but it is churn in the dependency tree, and this is not the day for it. Run npx expo install --check after the pilot week, not before the handover.

F19

Dead code left over from the mock-data era LowOpen

isResidential in lib/duties.js:21 is defined and never called — and it tests row.stype, the raw database spelling, where the live filter two functions below correctly tests the mapped s.type code. It would read as the authority on the rule and is not one. data/mockData.js still exports STAFF, DUTIES and SEED_RECORDS, none of which any screen uses; only STATUS_META and SPANNING are live.

F20

useSyncExternalStore has no server snapshot LowOpen

The shared clock in lib/clock.js omits the third argument. Harmless on device; it would throw if the web build were ever server-rendered.

Build it again

The fix is in the repository. This is the command that produces an installable APK with the configuration compiled into it. 

npx eas build --platform android --profile preview

Check the build log for the line listing the environment variables in scope. If EXPO_PUBLIC_SUPABASE_URL is not among them, the app will open on the “not set up yet” screen instead of the login — which is now the honest failure, rather than a crash.
