CHANGES MADE ON 2026-11-10 (Expo app) — TO REPEAT IN THE WEB DASHBOARD
=====================================================================

Two features:
  A. Gate notifications: every student sign-out / sign-in at the gate goes to
     Coordinator, MOD (management) and Admin, with an inbox to catch up on
     anything missed. Teachers can sign a student out from the marking screen.
  B. Staff logins with a temporary password: a coordinator adds staff WITH a
     working login (Initial@123 or random), can see/copy the ID + temporary
     password, and the staff member must choose their own password on first
     sign-in.

=====================================================================
A. GATE NOTIFICATIONS  (migration 047)
=====================================================================

A1. DATABASE (already done by 047)
---------------------------------
Table `notifications`
  id            bigserial PK
  kind          text  'student_out' | 'student_in'
  admission_no  text  -> students
  leave_id      bigint -> student_leave
  status        text  (H / O / S / G — the leave status)
  reason        text  (note typed at sign-out)
  expected_back date
  actor         text  -> staff.id   (who signed them out/in)
  actor_role    text  (role of that person: teacher, reception, ...)
  created_at    timestamptz

Table `notification_reads`  (per person — one coordinator reading a notice
does NOT hide it from the Principal)
  notification_id, staff_id, read_at     PK (notification_id, staff_id)

Rows are written ONLY by a trigger on `student_leave`:
  - INSERT on student_leave            -> 'student_out'
  - UPDATE where in_at goes null->set  -> 'student_in'
  The person who did it gets an automatic read-mark (they aren't told about
  their own action).

Who can read: coordinator, management, admin (function
`receives_notifications()`). Teachers / nurse / reception get ZERO rows, not
an error. Nobody can insert/update/delete notifications from a client.

RPC:
  mark_notifications_read(p_ids bigint[] default null)
     -> marks those ids read for the caller; NULL = mark ALL read.

Realtime: `notifications` is added to the `supabase_realtime` publication.
Realtime respects the read policy, so only the 3 roles receive events.

Gate permissions (unchanged, from 039): sign_student_out / sign_student_in
are allowed for reception, teacher, coordinator, admin.

A2. CLIENT DATA LAYER  (Expo file: src/lib/notifications.js)
-----------------------------------------------------------
Fetch (newest first, with the caller's read flag):
  supabase.from("notifications")
    .select("*, notification_reads(staff_id)")
    .order("created_at", { ascending: false })
    .limit(200)
  read = row.notification_reads.some(r => r.staff_id === myStaffId)
  (notification_reads is filtered by RLS to your own rows anyway)

Mark read:
  supabase.rpc("mark_notifications_read", { p_ids: [id, ...] })   // some
  supabase.rpc("mark_notifications_read", { p_ids: null })        // all

Live:
  supabase.channel("gate-notices-<random>")
    .on("postgres_changes",
        { event: "INSERT", schema: "public", table: "notifications" },
        payload => onInsert(payload.new))
    .subscribe()
  // unsubscribe: supabase.removeChannel(channel)

If the table doesn't exist yet (server without 047), treat as empty list.

A3. CLIENT STATE  (Expo: src/context/NotificationsContext.js)
------------------------------------------------------------
Only active when user.role is coordinator / management / admin
(Expo: receivesGateNotices(role) in src/domain/roles.js).

Provides: { enabled, items, unread, loading, error, refresh, markRead(ids),
            markAllRead(), describe(n) }

On start: fetch list, subscribe to realtime, and refetch when the app/tab
regains focus (web: `visibilitychange` / window focus).

When a realtime INSERT arrives:
  - prepend it to the list (skip duplicates by id)
  - if actor === me -> mark it read locally, no alert
  - otherwise: show a toast, and (phone only) a system notification
    (web: optionally the browser Notification API, if you want)
  - refresh the open-leaves list so the Gate page / marking locks update
    (Expo added `refreshLeaves()` to SchoolDataContext: refetch only
    student_leave where in_at is null — NOT a full reload)

Text of a notice — describe(n):
  student name + class label come from the students register by admission_no
  "by" = "you" if actor is me, else "<staff name> · <role label>"
  student_out:
     title: "<Name> (<Class>) signed out · <Status label e.g. Home>"
     body:  "Signed out by <by> — <reason>"   (reason part only if present)
  student_in:
     title: "<Name> (<Class>) is back on campus"
     body:  "Signed in by <by>"
  extra line: time, and for sign-outs "expected back <date>" if set.

B. STAFF LOGINS WITH A TEMPORARY PASSWORD  (migration 048)
=====================================================================

B1. RULES
---------
- Coordinator or admin only. A coordinator may act on teacher / nurse /
  reception; coordinator / management / admin accounts are the admin's.
  Nobody acts on their own account (use normal Change password).
- Temporary password = "Initial@123" (school default) or random:
  5 letters + "@" + 3 digits, no look-alike characters (no 0/O/1/l/I),
  e.g. "AtEGD@672".
- The coordinator can see a staff member's password ONLY while it is still
  the temporary one. Once the person chooses their own it is deleted —
  nobody can read it (Supabase stores a bcrypt hash only). Forgot it ->
  coordinator gives a new temporary password.
- Setting/resetting a temp password signs the person out everywhere.
- First sign-in with a temp password: the app shows ONLY a
  "Choose your password" screen until they set their own.

B2. DATABASE (already done by 048)
---------------------------------
  staff.must_change_password  boolean default false
  table staff_temp_passwords(staff_id PK, password text, kind 'default'|'random',
                             issued_by, issued_at)  — no client access at all

RPCs (call these; never write the tables):
  add_staff_member_with_login(p_name, p_email, p_phone, p_role,
                              p_class_key, p_random boolean)
     -> [{ staff_id, temp_password }]
     Same validation as add_staff_member (036): name >= 2 chars, valid
     email, email not already on staff, class must exist, coordinator may
     only add role 'teacher'. Creates the Supabase Auth user (email already
     confirmed — no confirmation email), links it, flags must_change.

  set_temporary_password(p_staff text, p_random boolean) -> text (the password)
     Creates a login if they have none, else resets it. Flags must_change.

  list_staff_logins() -> rows { staff_id, has_login, must_change,
                                temp_password, kind, issued_at }
     Only for staff the caller may manage. temp_password is null once they
     have chosen their own.

  change_my_temporary_password(p_password text) -> void
     For the signed-in person. Refuses < 8 chars, refuses the same temp
     password and "Initial@123". Clears must_change and deletes the temp copy.

A trigger also clears must_change + the temp copy if the password changes
any other way (reset code, normal Change password).

The old one-time reset code (issue_password_reset / redeem_password_reset)
still exists and is still offered as a third option.

B3. CLIENT DATA LAYER  (Expo: src/lib/staff.js)
----------------------------------------------
  staff row mapping: add  mustChangePassword: !!row.must_change_password

  addStaffMemberWithLogin({name,email,phone,role,classKey,random})
     -> rpc add_staff_member_with_login -> { staffId, password }
  setTemporaryPassword(staffId, random) -> rpc set_temporary_password -> password
  fetchStaffLogins() -> rpc list_staff_logins -> map by staff_id
     { hasLogin, mustChange, tempPassword, kind, issuedAt }
     (on error return {} so an old server doesn't break the page)
  changeMyTemporaryPassword(pw) -> rpc change_my_temporary_password

  loginDetailsText({name,email,password}) =
     "BG-SAAR login for <name>\n" +
     "ID: <email>\n" +
     "Password: <password>\n" +
     "You will be asked to set your own password the first time you sign in."
