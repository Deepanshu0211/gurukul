dummy data only, no backend yet
  1. 01 Set up the frontend project UI / UX ▸

    React + Vite, built as a PWA — no backend calls yet, just the project shell.

    What it means

    Start purely on the frontend. Get a blank app running and installable to a phone home screen before touching any data. The existing prototype (gurukula-attendance-prototype.jsx) is the visual reference for layout, spacing and tone — port its look, not necessarily its file structure.

    Suggested names

    gurukula-attendance/app/ src/screens/ src/components/ src/lib/ main.jsx
    Source: self-build-guide.md §2 (project structure).
  2. 02 Build the main screen shell — 3 options UI / UX ▸

    The role switch can be a fake dropdown for now — just prove the layout works for all three.

    What it means

    One shell component that shows/hides three sections depending on a (fake, hardcoded for now) role value. Don't wire real auth yet — just prove a teacher's view genuinely never renders the other two tabs.

    • Mark Attendance — every role sees this
    • Roster & People — Coordinator/Admin only
    • Reports & Alerts — Management/Coordinator/Admin only

    Suggested names

    App.jsx AppShell.jsx screens/MarkAttendance.jsx screens/RosterPeople.jsx screens/ReportsAlerts.jsx currentRole
    Source: gurukula-attendance-prototype.jsx (nav pattern, simplified from its 4 tabs to 3).
  3. 03 Build the Mark Attendance screen (dummy data) UI / UX ▸

    The most important screen in the app — get this feeling fast before it's ever real.

    What it means

    • A duty list: "My duties today," each tagged with a status chip — Upcoming / Due now / Submitted / Overdue
    • Tapping a duty opens a student list grouped by class, everyone defaulting to Present
    • Tap a name to toggle Absent; a small per-row menu for Home / Sick / Activity / Outing / Self study
    • A running counter at the bottom: "Present 46 · Absent 1 · Home 2"
    • Use a small hardcoded array of fake students/duties for now — wire real data in Phase 3

    Suggested names

    screens/MarkAttendance.jsx components/DutyCard.jsx components/StudentRow.jsx components/StatusChip.jsx components/StatusMenu.jsx duty.state pendingStatuses

    Naming trap to avoid: the four chips (Upcoming/Due now/Submitted/Overdue) are a computed UI label, not a stored value — keep that separate in your head from the database's own duty_state enum, which only ever stores pending or submitted. Upcoming/Due/Overdue get worked out client-side from the current time.

    Source: Attendance_System_Requirements_v1.docx §7 (A1-A4); gurukula-attendance-prototype.jsx (TeacherView, dutyStatus()).

Phase 2 · Backend

once the screens feel right
  1. 06 Set up the backend accounts Backend ▸

    Supabase, GitHub, Vercel, and an email-sending service — nothing else needed.

    What it means

    No traditional "server" here. Four free accounts cover the entire backend:

    • Supabase (region: Mumbai) — database, login system, security rules, and scheduled jobs, all in one
    • GitHub (private repo) — code lives here; pushing can auto-deploy
    • Vercel, connected to that repo — hosts the live app with HTTPS
    • Brevo or Resend — the email API that sends summaries and alerts (one verified sender address needed, e.g. alerts@yourschooldomain)

    Suggested names

    supabase/ supabase/migrations/ supabase/functions/ .env / .env.local
    Source: self-build-guide.md §1 (stack rationale) and §5 M0.
  2. 07 Create the database tables Backend ▸

    Run the schema once as migration 001 — it's already written.

    What it means

    The full SQL already exists in self-build-guide.md §3 — copy it in as-is. Keep these exact table names; the UI code from Phase 1 should be re-shaped to match them, not the other way around.

    Suggested names (these are fixed — use exactly these)

    students staff checkpoints duty_defaults duties attendance status_types spanning_statuses alerts audit_log

    Also create the Module F tables now (gate_passes, sickbay_admissions) — ignore them for this sprint, but creating them now avoids a rebuild later.

    Source: self-build-guide.md §3 (full SQL); Attendance_System_Requirements_v1.docx §4.
  3. 08 Import the real student & staff list Backend ▸

    One-time, re-runnable script from the school's existing Excel register.

    What it means

    Column names should map 1:1 to Student_List_2025-26.xlsx so re-imports never need reformatting. Skip rows whose Admission No. already exists (safe to re-run). Also seed checkpoints and create logins for ~5 pilot staff.

    Suggested names

    scripts/import_students.py admission_no
    Source: self-build-guide.md §5 M1a; Attendance_System_Requirements_v1.docx §12 (D1-D2).
  4. 09 Build login + role-based access Backend ▸

    The database itself blocks cross-role access, not just the UI.

    What it means

    Every staff member gets one Supabase Auth login. Their staff.role value decides what renders — this replaces the fake role dropdown from Phase 1, Step 2. Turn on Row-Level Security (RLS) on every table now, not as a later pass: it means the database refuses a teacher's query for another class's data, even from the raw network console.

    Suggested names

    lib/supabase.js role: teacher | coordinator | management | admin my_staff() useSession()
    Source: self-build-guide.md §3 (RLS policies); Attendance_System_Requirements_v1.docx §14 (P1-P2).

Phase 3 · Connect the UI to real data

Phase 1 screens, now wired for real
  1. 10 Wire Mark Attendance to real data + Submit → lock → email Connect & harden ▸

    Swap the dummy array for live duties; one atomic save on submit.

    What it means

    • A single Postgres function submit_duty(duty_id, rows) saves every mark and locks the duty in one all-or-nothing step
    • Once locked, re-opening shows read-only; corrections go through a Coordinator and get logged
    • An Edge Function send-summary fires right after: emails Coordinator + MOD + Principal, e.g. "Breakfast Senior 138/149 present · 2 ABSENT"

    Suggested names

    submit_duty(duty_id, rows) supabase/functions/send-summary/
    Source: self-build-guide.md §4; Attendance_System_Requirements_v1.docx §9 (N3) and §7 (A6-A7).
  2. 11 Build the safety alert Connect & harden ▸

    The actual reason this app exists — catches a child going missing during the day.

    What it means

    Inside send-summary: for every student marked Absent, check whether an earlier checkpoint today already has them Present or accounted-for. If so, insert into alerts and email Coordinator + MOD + Principal immediately with name, class, house, and last-seen checkpoint. Never auto-close — only a logged remark closes it.

    Suggested names

    alerts.kind = 'present_then_absent' alerts.close_remark
    Source: Attendance_System_Requirements_v1.docx §10 (F1, F4).
  3. 12 Build reminders & escalation Connect & harden ▸

    A scheduled job checks for missed checkpoints every 5 minutes.

    What it means

    • 10 min before window close, still unmarked → email the assigned teacher
    • At window close → email Coordinator + MOD; 10 min later → email Principal
    • Meal and night checkpoints escalate to the Principal immediately on miss
    • A nightly job copies roster defaults into today's actual duty list

    Suggested names

    supabase/functions/cron-reminders/ supabase/functions/cron-generate-duties/ duties.reminder_sent duties.escalated_l1 / escalated_l2
    Source: self-build-guide.md §4; Attendance_System_Requirements_v1.docx §9 (N1-N2) and §6 (C2).
  4. 13 Wire Roster & People and Reports & Alerts to real data Connect & harden ▸

    Swap the dummy data in Phase 1's Steps 4 & 5 for live queries.

    What it means

    • Reassign-duty picker now writes to duties.staff_id for a one-day override
    • Add/edit/deactivate now writes to students/staff (deactivate sets a flag + leaving date, never deletes)
    • Reports feed now reads live attendance/alerts; CSV export becomes a real download
    Source: Attendance_System_Requirements_v1.docx §8 (B1-B5), §11 (R1, R6), §12 (D3).
  5. 14 Security test the access rules by hand Connect & harden ▸

    Prove a teacher account cannot see another class's data — before the pilot, not after.

    What it means

    Log in as a real teacher account, open the browser dev console, try to directly query another class's attendance or students rows. Confirm RLS blocks it at the database level. Repeat for each role.

    Source: self-build-guide.md §3; Attendance_System_Requirements_v1.docx §14 (DPDP Act 2023).

Phase 4 · Launch

  1. 15 Run the real pilot Launch ▸

    2 class-sections + 1 meal band, one week, on paper in parallel.

    What it means

    • 2 real class-sections + 1 prasadam band mark digitally for one week
    • Keep paper running in parallel that same week
    • Fix friction daily; don't move to full rollout until teachers stop needing to ask questions

    If the 2 weeks run short: everything through Step 12 (the safety alert) must be solid. Step 13's screens can ship thinner without breaking the pilot.

    Source: self-build-guide.md §5 M1c; Attendance_System_Requirements_v1.docx §17 (M1 acceptance).
